# Deep Research Pipeline Investigation Report

## Executive Summary

The Deep Research pipeline consists of a Planner agent, a multi-phase Researcher agent with sub-agents (Summarizer, Reflector), and a Writer agent. The pipeline is orchestrated in `lib/main.dart` and backed by a Python bridge (`orchestrator.py`) that persists evidence to `temp.json`.

While the intended design is that the planner only plans phase structure and the phase-1 prompt, and each phase authors the next phase's prompt from its actual findings, the implementation has several critical flaws. The most severe is a **resume bug that causes complete inter-phase evidence loss**. Additionally, the planner's static prompts for later phases can contain stale entity guesses that spoil research quality.

---

## 1. Planner: Output, Flow, and Stale Content Spoilage

### Finding 1.1: Planner emits static prompts for ALL phases upfront, including later phases that depend on earlier results.

**Symptom**: Later phases (e.g., Phase 2) receive static `queryText` from the planner that may contain hardcoded entity names (e.g., "Find specs for GPT-4, Claude 3"). When Phase 1 actually discovers different entities (e.g., "GPT-5, Claude 4"), Phase 2's prompt contains conflicting instructions.

**Root Cause**: 
- `lib/services/deep_research/deep_research_prompts.dart:26-27`: The planner system prompt explicitly instructs it to generate full prompt text for all phases, including examples like "Phase 1: Discover all free flagship coding models... → Phase 2: For each coding model discovered in previous phases, find their specifications...".
- `lib/main.dart:5294-5320`: The planner output is parsed into `plannedSteps`, where each step's `query_text` is the full static prompt text generated by the planner.
- `lib/main.dart:5532`: This static `queryText` is injected into every phase's prompt as `Focus Area Instructions: $queryText`.
- `lib/main.dart:5535`: The `crossPhaseContext` block (with actual discovered entities) is injected separately as `PREVIOUS PHASE RESULTS (MANDATORY RESEARCH TARGETS)`.
- The result is that the researcher receives two conflicting sets of instructions: the planner's static `Focus Area Instructions` (which may contain old guesses) and the `PREVIOUS PHASE RESULTS` block (with actual entities). The researcher may follow the stale planner text instead of the actual evidence.

**Fix Suggestion**: 
- Change the planner to only emit a brief **scope** and **dependency declaration** for later phases, not full prompt text. For example, instead of "For each coding model discovered in previous phases, find specs", the planner should emit `{"title": "Find Specs", "depends_on": "phase_1", "scope": "Find specifications for all entities discovered in the dependency phase"}`.
- The phase prompt should then be dynamically constructed from the `scope` and the actual `crossPhaseContext`, not from static planner text.
- Alternatively, if keeping the current planner output format, strip any specific entity names from later phases' `queryText` before injecting it into the prompt, leaving only the generic instruction.

## 2. Inter-Phase Data Flow: Persistence and Evidence Loss

### Finding 2.1: CRITICAL — Resume bug causes complete inter-phase evidence loss.

**Symptom**: When resuming a research run where Phases 1 and 2 are already completed, Phase 3 receives an empty `crossPhaseContext`. It cannot see any facts, findings, or entities from Phases 1 and 2, effectively researching blind.

**Root Cause**:
- `lib/main.dart:5366-5370`: `crossPhaseContext` is initialized as an empty `StringBuffer()` at the start of `_runResearchLoop`.
- `lib/main.dart:5384-5387`: When resuming, phases with `status == 'completed'` or `status == 'completed_with_issues'` are skipped via `continue`.
- `lib/main.dart:6611-6651`: `crossPhaseContext` is only built from `phaseFacts` and `phaseFindings` *after* a phase executes. Skipped phases never execute, so they never contribute to `crossPhaseContext`.
- The evidence for completed phases *is* persisted in `temp.json` (via the Python bridge), but it is never loaded back into `crossPhaseContext` for subsequent phases.

**Fix Suggestion**:
- After loading a usable plan for resume, iterate through all already-completed phases and rebuild `crossPhaseContext` from `temp.json` before starting the first pending phase.
- Alternatively, change `crossPhaseContext` to be populated lazily from `temp.json` at the start of each phase, querying for all phases with index < current index.

### Finding 2.2: Batch summarization failure silently loses all fetched text.

**Symptom**: If the batch summarization LLM call fails, all facts and findings from the fetched URLs in that phase are lost. `phaseFacts` remains empty, and the phase contributes nothing to `crossPhaseContext` or `temp.json`.

**Root Cause**:
- `lib/main.dart:6345-6463`: The batch summarization is wrapped in a try-catch. On failure, the error is logged, and the fetched texts (`fetchedTexts`) are discarded.
- `lib/main.dart:6447-6457`: The `catch` block marks the fetch events as failed but does not attempt to re-summarize or fall back to raw text.
- `lib/main.dart:6611`: Since `phaseFacts` is empty, `crossPhaseContext` is not updated for this phase.
- The phase is not marked as failed (unless other errors occurred), so it proceeds as if it had no evidence.

**Fix Suggestion**:
- On batch summarization failure, fall back to individual summarization for each URL, or store the raw fetched text as low-confidence findings so the evidence is not completely lost.
- Mark the phase as `completed_with_issues` and add an execution issue so the writer knows evidence was lost.

### Finding 2.3: `crossPhaseContext` only includes a subset of evidence.

**Symptom**: Phase N+1 only sees 15 facts and 8 findings from each previous phase, even if more were collected.

**Root Cause**:
- `lib/main.dart:6638`: `for (final f in phaseFacts.take(15))` — only first 15 facts included.
- `lib/main.dart:6642`: `for (final f in phaseFindings.take(8))` — only first 8 findings included.
- `lib/main.dart:6378-6388`: `phaseFacts` is capped at 20 per phase, so 5 facts are always dropped from context.
- This can cause Phase N+1 to miss important entities or facts that were discovered but not in the first 15/8.

**Fix Suggestion**:
- Increase the limits or make them dynamic based on context size.
- Prioritize facts/findings that introduce new entities (subjects) over those that just add more data for existing entities.

### Finding 2.4: `crossPhaseContext` is unbounded and can blow up prompt size.

**Symptom**: With 12 phases, each contributing 15 facts and 8 findings, `crossPhaseContext` can grow very large, potentially exceeding the model's context window.

**Root Cause**:
- `lib/main.dart:5370`: `crossPhaseContext` is a `StringBuffer` with no size limit.
- `lib/main.dart:5535`: It is injected directly into the phase prompt.
- There is no truncation or budgeting for `crossPhaseContext`.

**Fix Suggestion**:
- Implement a token budget for `crossPhaseContext` (e.g., 4000 tokens). When it exceeds the budget, drop low-confidence facts or older phases' findings.
- Alternatively, only include entities and source URLs from older phases, not full facts/findings, to keep the context compact.

## 3. Handoff Chain

### Finding 3.1: Handoff chain is wired end-to-end but parsing is fragile.

**Symptom**: Phase N writes `next_brief` for Phase N+1 via `step_complete`. Phase N+1 receives it as `handoffBrief`. However, if the JSON is malformed, `handoffBrief` is silently empty.

**Root Cause**:
- `lib/main.dart:5716-5773`: When `stepCompleteRequested`, the code manually parses the JSON to extract `next_brief`.
- `lib/main.dart:5761-5763`: Uses `DeepResearchHelpers.parseJsonObject`, which uses regex to find the first JSON object.
- `lib/main.dart:5768-5770`: If `brief` is empty, `steps[i + 1]['handoff_brief']` is not set.
- No error is logged, and the phase continues without a handoff brief.
- `lib/main.dart:5517-5533`: The next phase's prompt checks `handoffBrief.isNotEmpty`. If empty, the `HANDOFF BRIEF` block is omitted entirely.

**Fix Suggestion**:
- Log a warning when `step_complete` is detected but `next_brief` cannot be parsed.
- If parsing fails, instruct the agent to re-emit `step_complete` with valid JSON.
- Use a more robust JSON extraction method (e.g., `_findNativeToolCalls`) instead of manual parsing.

### Finding 3.2: Phase 1 correctly receives only the planner's phase-1 prompt.

**Symptom**: Phase 1 has no `handoffBrief` and no `crossPhaseContext`, so it receives only the planner's `queryText`.

**Status**: This is correct behavior. No issue.

## 4. Write Agent

### Finding 4.1: Final report is assembled correctly but `compactText` optimization is dead code.

**Symptom**: The writer always receives JSON evidence, never compact text, despite code paths suggesting compact text is preferred.

**Root Cause**:
- `lib/main.dart:6790`: `writerEvidence = compactText.isNotEmpty ? compactText : tempJsonContent`.
- `lib/main.dart:6737`: `compactText` is read from `writerExport['compact_text']`.
- `python_bridge/deep_research/orchestrator.py:383-389`: `export_for_writer` returns only `content`, `token_estimate`, `truncated_facts`, `truncated_findings`, `truncated_phases`. It does NOT return `compact_text`.
- Therefore, `compactText` is always empty, and `writerEvidence` is always `tempJsonContent` (JSON).

**Fix Suggestion**:
- Either implement `compact_text` generation in `orchestrator.py` (e.g., as a formatted text summary instead of JSON), or remove the dead code path in Flutter.

### Finding 4.2: Writer failure modes are handled but truncation is silent.

**Symptom**: If the writer produces an empty report or fails after 3 retries, the user sees an error. However, if evidence is truncated to fit the budget, the writer is informed via `executionIssues`, but the final report may be missing key evidence without the user knowing.

**Root Cause**:
- `lib/main.dart:6758-6771`: Truncation details are added to `executionIssues`.
- `lib/main.dart:6844-6845`: `executionIssues` are passed to the writer.
- `deep_research_prompts.dart:214`: Writer is instructed to note evidence gaps.
- However, the writer may not always disclose this clearly, and the user may not read the `executionIssues` JSON.

**Fix Suggestion**:
- Surface evidence truncation warnings in the UI (e.g., as a warning banner below the report).
- Include a "## Evidence Budget" section in the final report detailing what was truncated.

### Finding 4.3: Report is saved to file and delivered to chat.

**Symptom**: The final report is saved to a Markdown file and inserted into the chat as a markdown artifact.

**Status**: This works correctly. `lib/main.dart:6959-6968` saves to file, `lib/main.dart:6992-7012` inserts into chat.

## 5. Other Quality Bugs and Feature Gaps

### Finding 5.1: Evidence deduplication is inconsistent between Flutter and Python.

**Symptom**: Flutter deduplicates facts by `metric|subject|value`, while Python deduplicates by `source|stage_id`. This means the same fact from two sources is kept in Python but may be dropped in Flutter.

**Root Cause**:
- `lib/main.dart:6057-6058`: `factDedupKey = '${item['metric']}|${item['subject']}|${item['value']}'`.
- `python_bridge/deep_research/orchestrator.py:84`: `key = f"{norm}::{stage_id}"` (source URL + stage ID).
- This inconsistency means the `temp.json` may have duplicate facts that Flutter already deduplicated, or vice versa.

**Fix Suggestion**:
- Align the deduplication logic. Prefer the Python bridge's approach (dedup by source URL) to preserve evidence from multiple sources.

### Finding 5.2: Crude entity extraction in `crossPhaseContext`.

**Symptom**: Entities extracted from findings include junk words (e.g., "The", "This") because the extraction only checks for capitalization, hyphens, or dots.

**Root Cause**:
- `lib/main.dart:6619-6629`: Splits finding text by whitespace and checks `clean.length > 3 && clean.length < 40 && (clean.contains('-') || clean.contains('.') || clean[0].toUpperCase() == clean[0])`.
- This is too permissive and includes common capitalized words.

**Fix Suggestion**:
- Use a more sophisticated entity extraction method (e.g., NER or regex for known patterns like model names, version numbers).
- Alternatively, only extract subjects from `phaseFacts`, which are more structured.

### Finding 5.3: Reflection gaps may be empty if all gaps were already executed.

**Symptom**: If the Reflector identifies gaps but all gap queries were already executed in previous phases, `gapText` is empty. The agent receives no guidance and may loop or fail.

**Root Cause**:
- `lib/main.dart:6529-6551`: Gaps are filtered against `executedQueries`. If all gaps are duplicates, `gapText` is empty.
- `lib/main.dart:6543-6549`: If `gapText.isNotEmpty`, a message is added. If empty, no message is added.
- The agent may then have no new searches to run and may emit `step_complete` or loop.

**Fix Suggestion**:
- If all gaps are duplicates, instruct the agent that coverage is sufficient and to proceed to `step_complete`.
- Alternatively, reformulate the gaps with different keywords or time ranges.

### Finding 5.4: `phaseFacts.clear()` placement is correct but fragile.

**Symptom**: `phaseFacts.clear()` is called at the start of each phase. If an exception occurs between clear and the end-of-phase `crossPhaseContext` build, evidence is lost.

**Root Cause**:
- `lib/main.dart:5378-5381`: Clears at start of loop iteration.
- `lib/main.dart:6611-6651`: Builds `crossPhaseContext` at end of loop iteration.
- If an unhandled exception occurs in between, the phase has no evidence, and `crossPhaseContext` is not updated.
- The global try-catch (line 7015) catches the error, but the phase is marked as failed.

**Fix Suggestion**:
- Move `phaseFacts.clear()` to the end of the loop iteration, after `crossPhaseContext` is built, or use a local variable for the current phase's evidence.

### Finding 5.5: Search result truncation is aggressive.

**Symptom**: Search results are truncated to 4000 characters, which may cut off important snippets.

**Root Cause**:
- `lib/main.dart:5937-5940`: `if (searchResult.length > 4000) { searchResult = searchResult.substring(0, 4000) + '\n\n...[truncated]'; }`
- This is done to manage prompt size but may lose relevant results at the end.

**Fix Suggestion**:
- Truncate at a sentence or result boundary rather than a hard character limit.
- Alternatively, prioritize results that contain the query keywords.

### Finding 5.6: URL content relevance filtering may be too aggressive.

**Symptom**: The bridge cleaner filters fetched pages to ~6000 chars based on keyword overlap with the query. This may remove important sections that don't contain exact keywords.

**Root Cause**:
- `python_bridge/deep_research/cleaner.py:88-91`: If `query` is provided and text > 6000 chars, filters by relevance.
- `lib/main.dart:6242-6246`: `relevanceQuery` is derived from `queryText` (first 2 parts split by ` - | | success:| Key questions:`).
- If `queryText` is complex, the split may produce a poor `relevanceQuery`.

**Fix Suggestion**:
- Increase the relevance budget or make it configurable.
- Use semantic similarity instead of keyword overlap.
- Fall back to truncation if relevance filtering removes too much.
